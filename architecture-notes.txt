Architecture Notes
==================

Authentication & RBAC flow
--------------------------
The system uses JSON Web Tokens (JWT) for authentication. When a user logs in via the `/api/auth/login` endpoint, they receive a JWT containing their `id` and `role`. 
All protected routes use the `authenticate` middleware to verify the JWT. 
Role-Based Access Control (RBAC) is implemented using the `authorizeRole` middleware, ensuring that only Principals can approve/reject content, and only Teachers can upload content.

Subject-based system design
---------------------------
Content is strictly categorized by `subject`. The `/content/live` API can optionally filter by subject.
The scheduling engine independently evaluates active content per subject, allowing multiple subjects to run their own rotations concurrently.

Upload handling approach
------------------------
File uploads are handled by the `multer` middleware. 
- It validates the file format (jpg, png, gif) and size (10MB limit). 
- Files are saved locally in the `uploads/` directory with a unique timestamped filename to prevent collisions.
- The path is stored in the PostgreSQL database.

Approval workflow design
------------------------
1. A Teacher uploads content, which defaults to `pending` status.
2. The Principal retrieves all content and reviews it.
3. The Principal can call the `approve` or `reject` endpoint.
4. If rejected, a `rejection_reason` is explicitly required and saved to the database.

Scheduling/rotation logic (VERY IMPORTANT)
------------------------------------------
Instead of using a background cron job that constantly updates a 'live' status in the database (which doesn't scale well), the scheduling logic evaluates the active content dynamically at request time:
1. The system fetches all `approved` content for the specified teacher that falls within the `start_time` and `end_time` windows.
2. The content is grouped by `subject`.
3. For each subject, the total rotation duration is calculated (Sum of all active content `rotation_duration`).
4. Using the current Unix Timestamp modulo the total rotation duration, the system determines the current position in the cycle.
5. The specific content corresponding to that time slice is returned.
This ensures continuous, synchronized looping across all client devices without database write overhead.

Database design decisions
-------------------------
PostgreSQL was chosen. We used two core tables: `users` and `content`.
`content` maintains all necessary state, including `status`, `start_time`, `end_time`, and `rotation_duration`.
The `status` field is implemented as an efficient integer check in the database (0=Uploaded, 1=Pending, 2=Approved, 3=Rejected) which strictly maps to a centralized TypeScript `ContentStatus` enum (`src/domain/enums/ContentStatus.ts`). This ensures strong type safety across our GraphQL layer, UseCases, and database.
By querying `start_time <= NOW() AND end_time >= NOW()`, we efficiently eliminate inactive content at the database level.

Clean Architecture & Folder Structure
-------------------------------------
The project rigorously follows Clean Architecture principles, leveraging the Awilix library for robust Dependency Injection. Responsibilities are strictly segregated across layers:

src/
├── domain/         (Core business entities, ContentStatus Enums, DTOs, Error types)
├── useCases/       (Application-specific business rules, orchestrating flows)
├── engines/        (Core business logic and scheduling logic algorithms)
├── controllers/    (Interface Adapters: Translating HTTP requests to UseCases)
├── repositories/   (Data access logic, interacting with the database/GraphQL)
├── infrastructure/ (Frameworks, WebServer, Routes, PostGraphile setup, Middleware, Logging)
├── config/         (Database connections and environment configurations)
├── jobs/           (Cron jobs or scheduled background tasks)
└── index.ts        (Application entry point)

Dependency Injection Flow
-------------------------
The dependency chain follows a strict inward-pointing rule:
Controllers -> UseCases -> Engines -> Repositories
The entire dependency chain is wired up inside `src/infrastructure/ioc/registry.ts` using Awilix, supporting proxy-based injection and ensuring decoupled, highly testable code.

Middleware usage
----------------
- `cors` and `express.json` for request formatting.
- `authenticate`: Validates JWT.
- `authorizeRole`: Enforces RBAC permissions.
- `upload`: Handles multipart form data for S3/local storage.

Scalability approach
--------------------
- The stateless JWT approach allows the application to be scaled horizontally across multiple servers.
- The dynamic scheduling algorithm completely eliminates the need for a distributed lock or queue for managing active content states.
- Static file serving (uploads) can be easily offloaded to an S3 bucket and CloudFront CDN.
- PostGraphile provides an automatic GraphQL layer, which can be easily cached and scaled using a tool like Apollo Federation if the platform grows.

Security Decisions
------------------
- **Rate Limiting**: To prevent abuse, we implement a multi-layered rate limiter. We use the client's IP, User Agent, and a hash of the request body/query as the key. This prevents single clients from flooding the system even if they vary small parts of the request.
- **Nonce (Number used Once)**: For state-changing mutations, we require a cryptographic Nonce. This protects against Replay Attacks and CSRF. Nonces are validated and then stored in Redis for 5 minutes to prevent re-use.
- **Fail-Open Security**: For resilience, if the Redis service is unavailable, the security middlewares are designed to fail-open with a logged warning, ensuring system availability while prioritizing uptime.

Storage Decisions
-----------------
- **Abstracted Storage**: Using Multer with a hybrid storage engine allows us to develop locally using the `uploads/` folder and deploy to S3 by simply changing an environment variable.
- **S3 Service**: A dedicated `S3Service` handles generating signed URLs and direct uploads, ensuring that we don't expose raw bucket URLs to the public.

Subject-based system design
---------------------------
Each content item is strictly associated with a `subject`. The system supports filtering by subject at the database level. For the public broadcasting API, the system identifies all approved and active content for a specific teacher and subject, then applies the rotation algorithm to ensure subject-independent broadcasting loops.

Scheduling/rotation logic (VERY IMPORTANT)
------------------------------------------
Instead of static, brittle "Content Slots" tables, we implement a **Dynamic Rotation Algorithm**:
1. **Selection**: We fetch all approved content for the teacher where `NOW()` is between `start_time` and `end_time`.
2. **Total Cycle**: We calculate the sum of all `rotation_duration` values for these active items.
3. **Current Offset**: Using the formula `(Date.now()) % (TotalCycleDurationInMs)`, we find the exact millisecond offset in the current continuous loop.
4. **Resolution**: We iterate through the active items until we find the one corresponding to that offset.
This ensures a perfectly continuous loop that is stateless, requires zero background jobs, and automatically adjusts as content is added or expires.
